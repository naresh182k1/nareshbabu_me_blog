# GitHub Copilot for *Enterprise*

## A Deep Dive on Adoption

*From scattered pilots to a governed, scaled rollout.*

**Agent Mode · Coding Agent · Custom Agents · MCP Servers · Agent HQ · Enterprise Governance**

---

## The Enterprise Problem

Most enterprises adopting GitHub Copilot today look like this:

- **Scattered pilots.** A few teams use Agent Mode in VS Code. A different team is experimenting with the cloud Coding Agent. Nobody has a shared mental model.
- **Unclear controls.** Security and platform teams cannot answer: *which agents are allowed, which models, which MCP servers, who reviews what?*
- **Inconsistent quality.** Without `AGENTS.md`, custom agents, or MCP servers in place, every developer gets a different experience and the tool fails to compound.
- **No measurement.** Adoption, accept rate, and PR throughput aren't tracked, so leadership can't tell whether the investment is paying back.

**The platform is ready for enterprise scale. Most adoption programs are not.**

---

## The Solution — A Five-Layer Adoption Model

A successful enterprise rollout aligns five distinct layers of the platform. Confusing them is the most common adoption mistake.

1. **Agent Mode (IDE)** — Synchronous developer experience
2. **Coding Agent (Cloud)** — Asynchronous issue-to-PR delivery
3. **Custom Agents** — Specialized, scoped personas via `.agent.md`
4. **MCP Servers** — Tools and data the agents can reach
5. **Agent HQ** — The enterprise control plane that ties it all together

The rest of this deck walks each layer, what it does, what it controls, and what an enterprise adoption program needs to put in place for each.

---

## Layer 1 — Agent Mode (IDE, Synchronous)

**What it is:** Copilot inside the IDE (VS Code, JetBrains) running a real-time agentic loop. The developer gives it a goal; it plans, edits multiple files, runs tests, and self-heals on errors — while the developer watches.

**Key control file:** `AGENTS.md` in the repo root. Defines coding standards, tool preferences, and guardrails. Version-controlled and shared with the team.

**Where it runs:** Local machine or Codespace. Synchronous — the developer is present while it works.

**Adoption requirements:**
- A repo-level `AGENTS.md` template that every team can fork
- Standards for tool preferences, guardrails, and review expectations
- Developer enablement on prompting and review patterns

**Reference:** [Agent Mode 101 — GitHub Blog](https://github.blog/ai-and-ml/github-copilot/agent-mode-101-all-about-github-copilots-powerful-mode/) · [Agent Mode + MCP Tutorial](https://docs.github.com/en/copilot/tutorials/enhance-agent-mode-with-mcp)

---

## Layer 2 — Coding Agent (Cloud, Async)

**What it is:** Assign a GitHub Issue to `@copilot` and walk away. It spins up a GitHub Actions ephemeral runner, writes code, runs tests, and opens a PR. Asynchronous — the developer comes back to a review.

**Key security facts:**
- Agent never pushes to main. Always opens a draft PR.
- Network firewall blocks external calls unless explicitly allowlisted.
- CODEOWNERS rules still apply.

**Adoption requirements:**
- Enterprise admin enables it via the Policies page
- Issue templates that produce well-scoped tasks the agent can succeed on
- Review workflow that treats agent PRs the same as human PRs (or stricter)

**Reference:** [About Copilot Cloud Agent — Docs](https://docs.github.com/copilot/concepts/agents/coding-agent/about-coding-agent) · [What's New (Feb 2026)](https://github.blog/ai-and-ml/github-copilot/whats-new-with-github-copilot-coding-agent/)

---

## Layer 3 — Custom Agents (Specialized Personas)

**What it is:** A Markdown file (`.agent.md`) that defines a specialist version of the coding agent — its name, model, tool list, and behaviour prompt. Drop it into `.github/agents/` and it appears in the agent picker.

**Three scopes:**
- **Repo-level:** `.github/agents/`
- **Org-level:** via `.github-private` repo
- **Enterprise-level:** also via `.github-private`, available across all org repos

**Adoption requirements:**
- A starter library of organization-approved custom agents (test-specialist, security-reviewer, migration-helper)
- Authoring guidelines so teams can build their own without diverging on quality
- A publishing workflow from repo → org → enterprise scope

**Reference:** [Creating Custom Agents — Docs](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/create-custom-agents) · [Browse Live Agent Examples](https://awesome-copilot.github.com/agents/)

---

## Layer 4 — MCP Servers (Tool Extensions)

**What it is:** Model Context Protocol — an open standard (Anthropic-originated, now industry-wide) for connecting agents to external tools and data sources. Each MCP server exposes typed tools: `get_incident(id)`, `list_oncall()`, etc.

**Enterprise control:**
- MCP is **disabled by default** for org/enterprise users. Admins must enable it.
- The allowlist in `.github/mcp.json` controls which servers agents can reach.
- The GitHub MCP Registry (in VS Code) lets developers discover and install servers in one click.

**Adoption requirements:**
- An approved-MCP-server allowlist (security, observability, ticketing, design system)
- A private MCP Registry for enterprise-internal servers
- OAuth and credential handling standards (`COPILOT_MCP_` secrets)

**Reference:** [MCP and Coding Agent — Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/mcp-and-coding-agent) · [Extending Coding Agent with MCP](https://docs.github.com/copilot/how-tos/agents/copilot-coding-agent/extending-copilot-coding-agent-with-mcp)

---

## Layer 5 — Agent HQ (Enterprise Control Plane)

*New since Universe 2025 — the centralized control plane for agentic development.*

**Policy:** Centralized control over which agents (Copilot, Claude, Codex, Gemini) are allowed per org or team. Manage model allowlists, MCP server access, and feature toggles from one place.

**Security:** Cloud agent firewall blocks external network access by default. Audit logs for all agent events. Agent sessions are steerable and inspectable in real time from Mission Control.

**Publishing:** Three-tier catalog — repo (`.github/agents/`), org, or enterprise (`.github-private`). Public community publishing via `github/awesome-copilot`. Private MCP Registry for enterprise-internal servers.

**Observability:** Copilot Metrics Dashboard (public preview) gives org-wide adoption, accept rate, and PR throughput. Usage API replaces old CSV exports. Cost and chargeback per team.

**Reference:** [Agent HQ Announcement — GitHub Blog](https://github.blog/news-insights/company-news/welcome-home-agents/) · [Well-Architected: Governing Agents](https://wellarchitected.github.com/library/governance/recommendations/governing-agents/)

## The Adoption Journey — Four Phases

A working enterprise rollout moves through four phases. Skipping ahead is the second-most-common failure mode (after confusing the layers).

1. **Orientation** — Establish the shared mental model across developers, platform, and security teams.
2. **Mechanics** — Get hands-on with Coding Agent and Custom Agents on real internal work.
3. **MCP + Governance** — Wire in the tool layer and the enterprise controls together.
4. **Synthesis** — Author the organization's standards and scale across teams.

The remaining slides walk each phase as a concrete, sequenced program — videos to watch, docs to read, and artifacts to build.

## What an Adoption Program Has to Build

Reading and watching only takes you so far. Every successful enterprise rollout produces these four artifacts — they are what turn a tool into a practice.

### ① An organization-wide `AGENTS.md` template
**Problem:** Agent Mode in VS Code ignores team standards unless they are encoded.
**Solution:** A forkable `AGENTS.md` template at the org level with coding style rules, tool preferences ("prefer GitHub MCP over web fetch"), guardrails ("never commit without running tests"), and approved MCP server preferences.

### ② A starter library of custom `.agent.md` files
**Problem:** A coding agent with a generic prompt produces generic results. A scoped persona produces targeted, reviewable output.
**Solution:** A curated set — `test-specialist.agent.md`, `security-reviewer.agent.md`, `migration-helper.agent.md` — published org-wide, each with explicit scope (e.g., test specialist cannot modify production code, must use the project test framework, reports coverage before/after).

---

## What an Adoption Program Has to Build (continued)

### ③ A governed MCP server allowlist + private registry
**Problem:** Until MCP servers are wired in, the agent is blind to internal systems (incidents, tickets, observability, design system).
**Solution:** An approved-server allowlist in `.github/mcp.json`, a private MCP Registry for internal servers, OAuth/credentials standards (`COPILOT_MCP_` secrets), and a published process for teams to request new servers.

### ④ An adoption measurement baseline
**Problem:** Without metrics, leadership can't tell whether the investment is paying back, and adoption stalls.
**Solution:** Stand up the Copilot Metrics Dashboard from day one. Establish baselines for adoption, accept rate, and PR throughput. Use the Usage API for cost and chargeback per team. Tie the metrics to a quarterly business review.

> **The reference for all four:** [Well-Architected — Governing Agents](https://wellarchitected.github.com/library/governance/recommendations/governing-agents/), [Microsoft Tech Community Copilot SDK Case Study](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/building-agents-with-github-copilot-sdk-a-practical-guide-to-automated-tech-upda/4488948).

- **Reviewed** real enterprise case studies (Mercedes-Benz, EY, Microsoft's own implementation) and adapted the patterns
